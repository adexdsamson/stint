<objective>
Define and export the single `HostAdapter` contract a platform builder implements (HOST-01): three async methods — `requestConsent`, `requestApproval`, and `notify(event: LifecycleEvent)` (D-15, D-16) — plus the core-owned timeout rule that treats a non-response or abort as deny (approval) / decline (consent), so deny-by-default enforcement is never delegated to third-party adapter code (D-17). `requestApproval` carries only a binding-redacted summary, the `ConnectorBinding`, and an opaque approval-request id — never raw arguments (D-18). This also provides the fresh-consent mechanism a lease extension requires (LIFE-05); the reducer already restricts `extend` to actor `user`, and the Phase 4 proxy will call `requestConsent` before dispatching an extend.

Purpose: one small, stable interface every host (the Phase 6 CLI reference adapter, and any platform builder's UX) implements; the timeout-as-deny rule living in core is what keeps a slow or buggy adapter from ever turning into an unsafe allow.
Output: `host-adapter.ts` (interface, LifecycleEvent union, request/decision types, and the two core-owned await wrappers) with tests.

Note: `workflow.human_verify_mode` is end-of-phase, so this plan uses automated verification only (no per-plan human-verify checkpoint). The binding-**hash** mechanics over resolved args are `[OPEN: Phase 4]`; Phase 2 only carries the opaque approval id (D-18).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party adapter code → approval/consent outcome | A slow, buggy, or hostile adapter must not be able to produce an unsafe allow/grant. |
| approval request → adapter | Raw call arguments must never cross into the adapter/UI (D-18). |
| out-of-band channel vs MCP elicitation | Approvals must not be satisfiable through the agent's own MCP client. |
