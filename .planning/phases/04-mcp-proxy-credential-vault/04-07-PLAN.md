<objective>
Detect customer-side OAuth revocation on the runtime hot path (D-09, PRXY-07): when an outbound call's refresh comes back `invalid_grant` (the narrow, positive revocation signal — never a `/revoke` 2xx), move the lease `active → revoked` with actor `provider` inside the per-lease transaction, deny the triggering call, and receipt it — while a mere transient upstream error never revokes.

Purpose: this is the lazy provider-revocation detection that hands off to Phase 5 teardown; it consumes the 04-05 classifier and the 04-06 ExecuteStage and adds only the `reduce`-into-`revoked` wiring plus the invalid_grant-vs-transient discrimination.
Output: `revocation.ts`, the dispatch `provider_revoked` branch, and the forced-`invalid_grant` detection test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authorization server → vault refresh | The provider's `invalid_grant` is the only positive revocation signal; a 2xx `/revoke` is not proof |
| provider event → lease state | Only a `provider`-actor `grant_revoked` may move the lease to `revoked`; the agent is never an actor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07-FR | Tampering | false revocation from a transient blip | high | mitigate | Only `invalid_grant` classifies as `provider_revoked` (D-09); transient errors feed the denied/error path, never `grant_revoked` |
| T-04-07-NR | Repudiation | silent non-revocation (RFC 7009 no-op) | high | mitigate | Detection driven by a positive `invalid_grant` via `Events.BeforeResponse`, never by a `/revoke` 2xx (Pitfall 2/5) |
| T-04-07-EA | Elevation of Privilege | acting on a revoked lease | high | mitigate | Transition applied inside the transaction; `evaluatePolicy` denies any subsequent call on a non-`active` lease |
</threat_model>
